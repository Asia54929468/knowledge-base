# 测试能力与实践方法

<div class="section-lead">结合业务分析、测试设计、问题定位和工程工具，提高测试判断与协作能力。</div>

## 测试人员能力与工具 { #tester-capability-toolkit }

测试能力由业务理解、设计方法、沟通协作和技术定位共同构成。工具用于放大分析和反馈能力，不能替代对业务目标与风险的判断。

### 测试人员常用能力与工具

- **业务分析能力**：理解业务目标、用户角色、规则、流程和风险。
- **测试设计能力**：能系统使用黑盒、白盒和经验技术减少漏测。
- **沟通协作能力**：准确表达问题、推动风险解决，并与产品、开发和运维协作。
- **问题定位能力**：通过日志、请求、数据库、代码和监控缩小问题范围。
- **编程能力**：用于编写自动化、构造数据、调用接口和开发测试工具。
- **HTTP 与网络基础**：理解请求响应、DNS、代理、TLS、缓存和常见网络故障。
- **SQL 与数据库基础**：查询和验证数据，理解事务、索引和一致性。
- **Linux 基础**：查看进程、端口、资源、日志、文件和网络状态。
- **Git 基础**：管理脚本和测试资产，理解分支、提交、合并和差异。
- **浏览器开发者工具**：检查 Elements、Console、Network、Application 和 Performance。
- **接口工具**：使用 curl、Postman、Apifox 等发送请求并保存测试集合。
- **缺陷与项目管理工具**：常见有 Jira、禅道、Azure DevOps 等。
- **持续集成工具**：常见有 Jenkins、GitHub Actions、GitLab CI 等。
- **监控与日志工具**：根据团队技术栈使用日志检索、指标监控和链路追踪平台。

## 通用测试思维清单 { #testing-thinking-checklist }

通用清单帮助在信息有限时快速打开思路。它不是必须逐项执行的固定模板，应结合业务价值、变更范围和故障影响选择重点。

面对一个功能时，可以从以下视角快速展开：

- **正常**：用户按照预期流程操作会怎样？
- **异常**：输入错误、依赖失败或操作不合法会怎样？
- **边界**：最小、最大、刚好达到和刚好超过限制会怎样？
- **空值**：缺少字段、空字符串、Null 或空集合会怎样？
- **格式**：类型、长度、精度、编码和特殊字符是否正确处理？
- **重复**：重复点击、重复请求、重复数据和失败重试会怎样？
- **状态**：不同状态允许什么操作，状态能否正确迁移？
- **顺序**：改变步骤顺序、跳过步骤或返回上一步会怎样？
- **中断**：网络断开、关闭页面、切后台或服务重启后能否恢复？
- **并发**：多人或多个请求同时操作同一资源会怎样？
- **权限**：未登录、不同角色、不同数据归属是否被正确限制？
- **时间**：超时、过期、跨天、月底、闰年、时区和夏令时会怎样？
- **数据**：数据量很大、关联异常、迁移或清理后会怎样？
- **兼容**：不同设备、浏览器、系统、版本和配置是否正常？
- **性能**：响应是否够快，负载增大后是否稳定？
- **安全**：输入能否被利用，敏感信息是否泄露，能否越权？
- **易用性**：用户是否看得懂、找得到、能撤销并从错误中恢复？
- **可靠性**：局部失败时能否容错、降级、重试和恢复？
- **可观察性**：出现问题时是否有足够日志、指标和追踪信息定位？
- **回归影响**：本次变更可能影响哪些上下游、公共组件和历史功能？
