## 测试执行、结果与证据 { #test-execution-and-evidence }

测试执行不只是把用例标记为通过或失败，还要记录版本、环境、数据和客观证据。无法判断或无法执行的情况也必须使用清晰状态表达。

### 测试执行与结果

- **Pass（通过）**：实际结果符合预期结果。
- **Fail（失败）**：实际结果与预期结果不一致。
- **Blocked（阻塞）**：因环境、依赖或其他缺陷导致用例无法继续执行。
- **Not Run（未执行）**：用例尚未运行。
- **Skipped（跳过）**：根据计划或条件主动不执行该用例。
- **Not Applicable（不适用）**：用例不适用于当前版本、平台或范围。
- **测试结果 / 测试结论（Test Result / Outcome）**：某次执行产生的实际输出以及依据预期作出的通过、失败或阻塞判断。
- **测试事件（Test Incident）**：测试过程中需要进一步调查的任何异常，不一定最终都会被确认为软件缺陷。
- **假阳性（False Positive）**：测试报告了失败或告警，但被测系统实际没有对应问题，常由错误断言、环境或工具造成。
- **假阴性（False Negative）**：测试显示通过或没有告警，但系统实际存在问题，风险通常高于假阳性。
- **执行证据**：截图、视频、日志、请求响应、数据库记录等能支持测试结论的材料。
- **测试日志**：记录执行时间、人员、环境、版本、结果和异常，便于追踪和复现。
- **测试重现性**：失败场景应能在明确条件下重复触发；偶现问题也需记录频率和上下文。

## 缺陷管理 { #defect-management }

缺陷管理将异常现象转化为可复现、可分派、可验证的工作项。概念、报告质量、影响分级和状态流转共同决定缺陷协作效率。

### 缺陷基本概念

- **Error / Mistake（人为错误）**：人在需求、设计、编码或操作中产生的错误。
- **Defect / Fault / Bug（缺陷）**：工作产品中不符合需求、规范或合理期望的问题。
- **Failure（失效）**：软件运行时因缺陷被触发而表现出的错误行为。
- **根本原因（Root Cause）**：导致缺陷产生或未被及时发现的深层原因。
- **缺陷触发条件**：使潜在缺陷表现为失效的输入、状态、环境或操作。
- **潜伏缺陷（Latent Defect）**：已经存在于系统中，但因触发条件尚未出现而没有表现为失效的缺陷。
- **缺陷屏蔽**：一个缺陷阻止另一个缺陷暴露，前者修复后后者才可能出现。
- **偶现缺陷**：只在特定时序、环境、负载或数据下出现，需加强上下文和日志记录。
- **已知问题（Known Issue）**：团队已经确认并记录、但当前版本仍未解决的问题，可能附带规避方案。

```text
人为错误 → 引入软件缺陷 → 特定条件触发 → 软件失效
```

### 缺陷报告

**常见字段**

- Bug 编号
- Bug 标题
- 所属项目 / 模块
- 发现版本
- 测试环境
- 前置条件
- 复现步骤
- 测试数据
- 预期结果
- 实际结果
- 严重程度
- 优先级
- 复现概率
- 截图 / 视频
- 日志 / 请求响应
- 提交人
- 负责人
- Bug 状态
- 修复版本

**高质量缺陷报告**

- **标题准确**：用“位置 / 条件 + 操作 + 异常结果”概括问题。
- **步骤最小且完整**：删除无关操作，但保留稳定复现所需的全部条件。
- **预期与实际明确**：避免只写“有问题”“结果不对”。
- **一次聚焦一个问题**：不同根因或不同现象通常应分别提交。
- **证据充分**：附带时间、账号、版本、日志、截图、视频和请求信息。
- **客观描述**：陈述事实和影响，避免情绪化或对责任作主观判断。
- **先查重再提交**：确认不是已有问题，并在重复缺陷中关联原记录。

### 缺陷严重程度与优先级

- **严重程度（Severity）**：缺陷对系统、业务、数据或用户造成的影响有多大。
- **优先级（Priority）**：缺陷需要多快被处理，由业务影响、发布时间、修复成本等共同决定。

**常见严重程度**

- **Blocker / 致命**：系统不可用、核心流程完全阻塞，且没有可接受的绕行方案。
- **Critical / 严重**：核心功能异常、数据丢失、安全风险或大面积用户受影响。
- **Major / 主要**：重要功能存在明显问题，但影响范围有限或存在替代方案。
- **Minor / 次要**：非核心功能异常，对主要业务影响较小。
- **Trivial / 轻微**：文案、样式、易用性等轻微问题或改进建议。

**常见优先级**

- **P0**：必须立即处理，通常会阻止发布或需要紧急修复。
- **P1**：高优先级，应在当前版本尽快解决。
- **P2**：正常优先级，按计划安排修复。
- **P3**：低优先级，可在后续版本处理。

> 严重程度和优先级并不完全对应。例如首页公司名称拼写错误可能严重程度低，但因影响品牌而优先级高。

### 缺陷生命周期

```text
New → Assigned / Open → Fixed → Retest → Verified → Closed
                          ↑          │
                          └─ Reopened┘
```

- **New**：新提交，尚未完成确认或分派。
- **Assigned / Open**：缺陷已确认并分派处理。
- **In Progress**：负责人正在分析或修复。
- **Fixed / Resolved**：开发认为问题已经解决，等待验证。
- **Retest**：测试人员正在执行确认测试。
- **Verified**：修复结果已验证通过。
- **Closed**：缺陷流程完成并关闭。
- **Reopened**：验证未通过或问题再次出现，重新打开。
- **Rejected / Not a Bug**：经评估不属于缺陷。
- **Duplicate**：与已有缺陷重复。
- **Deferred**：确认存在，但延期到后续版本处理。
- **Cannot Reproduce**：当前条件下无法复现，需要补充信息或继续观察。
- **Won't Fix**：团队明确决定不修复，通常需要记录理由和风险接受者。

## 缺陷分析与过程改进 { #defect-analysis-and-improvement }

缺陷分析关注的不只是数量，而是缺陷为何产生、为何逃逸以及如何预防。指标应服务于趋势判断和过程改进，不能脱离上下文评价个人。

### 缺陷分析

- **缺陷分类**：可按模块、类型、来源、原因、严重程度、阶段和状态分类。
- **根因分析（RCA）**：寻找缺陷产生以及逃逸到后续阶段的根本原因，并制定预防措施。
- **五问法（5 Whys）**：连续追问“为什么”，逐步从表面现象定位深层原因。
- **鱼骨图**：从人员、流程、工具、环境、需求、技术等维度分析可能原因。
- **缺陷密度**：单位规模中发现的缺陷数量，可用于趋势分析，但不能脱离复杂度和风险单独评价质量。
- **缺陷逃逸**：应在较早阶段发现的缺陷直到后续阶段或生产环境才被发现。
- **缺陷泄漏（Defect Leakage）**：缺陷未在某测试阶段被发现而流入下一阶段；生产环境发现通常称为生产缺陷或线上逃逸。
- **缺陷拒绝率**：被拒绝、判为非缺陷或重复的缺陷占提交缺陷的比例，只能辅助分析需求理解和报告质量，不能脱离上下文评价个人。
- **缺陷趋势**：观察新增、修复、重开和遗留缺陷随时间的变化，判断质量是否趋于稳定。
- **缺陷老化**：缺陷从提交到当前或关闭所经历的时间，用于识别长期未处理问题。
- **缺陷清除效率（DRE）**：衡量发布前发现缺陷占发布前后已知缺陷总量的比例。

## 覆盖、风险、度量与发布决策 { #coverage-risk-metrics-release }

覆盖率说明测试触达范围，风险说明测试投入优先级，准入准出和报告则把证据转化为发布判断。任何单一数字都不能独立证明质量。

### 测试覆盖率与追踪

- **需求覆盖率**：被至少一个测试用例覆盖的需求占全部需求的比例。
- **风险覆盖率**：已被测试的已识别风险占全部关键风险的程度。
- **功能覆盖率**：测试涉及的功能点占计划功能点的比例。
- **用例执行率**：已执行用例占计划执行用例的比例。
- **用例通过率**：通过用例占已执行用例的比例。
- **代码覆盖率**：测试执行期间被运行的代码结构比例，如语句、分支和条件覆盖。
- **接口覆盖率**：被验证的接口、方法、参数和业务场景的覆盖程度。
- **平台覆盖率**：测试涉及的操作系统、浏览器、设备和配置占目标组合的程度。
- **需求追踪矩阵（RTM）**：建立需求、测试用例、执行结果和缺陷之间的对应关系。

> 覆盖率说明“测到了多少”，不直接说明“测得有多好”。覆盖对象、断言质量和风险选择同样重要。

### 测试准入与准出

- **准入标准（Entry Criteria）**：开始测试前应满足的条件，如需求基线确定、版本部署成功、环境和数据准备完成。
- **暂停标准**：当环境不可用、阻塞缺陷过多或版本质量过低时，暂时停止测试的条件。
- **恢复标准**：暂停问题解决后重新开始测试需要满足的条件。
- **准出标准（Exit Criteria）**：结束测试所需条件，如核心用例通过、重大缺陷关闭、风险被接受和报告完成。
- **完成定义（Definition of Done）**：团队对工作项“完成”的共同标准，通常包含开发、评审、测试和文档要求。
- **发布标准**：综合质量、业务、运维、安全和合规信息判断版本是否可以上线。

### 测试风险

- **产品风险**：软件可能在功能、性能、安全、可靠性等方面失效，从而影响用户或业务。
- **项目风险**：人员、进度、预算、环境、工具和依赖问题可能影响测试活动完成。
- **风险等级**：常根据“发生概率 × 影响程度”评估，也可考虑可检测性和暴露频率。
- **风险识别**：从需求复杂度、技术新颖性、变更频率、缺陷历史、业务价值和用户规模等方面识别。
- **风险缓解**：增加评审、提高测试深度、提前搭建环境、自动化回归或准备替代方案。
- **风险规避**：改变设计、范围或计划，消除风险来源。
- **风险转移**：通过合同、保险或第三方服务转移部分责任，但无法转移全部质量责任。
- **风险接受**：明确了解风险后决定承担，应记录理由、影响和批准人。
- **剩余风险**：采取措施后仍然存在的风险，需要在测试报告和发布决策中说明。

### 测试报告与测试度量

- **测试进度**：计划与实际的用例设计、执行和缺陷处理进展。
- **测试结果**：通过、失败、阻塞、未执行和不适用用例数量及比例。
- **缺陷情况**：按严重程度、优先级、模块和状态统计缺陷。
- **覆盖情况**：需求、风险、功能、环境和代码等覆盖程度。
- **遗留问题**：未解决缺陷、已知限制、绕行方案和潜在影响。
- **质量风险**：说明已经降低、仍然存在以及需要业务接受的风险。
- **测试结论**：基于证据说明是否达到准出标准，并给出发布建议。
- **经验总结**：记录有效实践、过程问题和后续改进措施。
- **度量原则**：指标用于支持判断和改进，不应脱离上下文，也不应简单用于个人绩效排名。
- **常见误区**：用例数量多、Bug 数量多或代码覆盖率高，都不能单独证明测试质量高。
