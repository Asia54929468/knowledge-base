# 测试分析、设计与准备

<div class="section-lead">把需求和风险转化为可执行、可复现、可维护的测试方案。</div>

## 需求分析与静态评审 { #requirements-and-static-reviews }

静态质量保障在程序运行前检查需求、设计、代码和其他工作产品。需求分析不仅确认写了什么，还要确认它是否正确、完整、一致、可行且可测试。

### 静态测试与评审

- **非正式评审**：无严格流程的同伴检查或快速反馈。
- **走查（Walkthrough）**：由作者带领参与者逐步查看工作产品并收集反馈。
- **技术评审（Technical Review）**：由技术人员评价方案是否正确、可行且符合规范。
- **审查（Inspection）**：角色和流程较正式，以系统识别缺陷为主要目标。
- **需求评审**：检查需求的正确性、完整性、一致性、明确性、可行性和可测试性。
- **设计评审**：检查架构、接口、数据模型、异常处理和非功能设计是否合理。
- **代码评审**：检查代码逻辑、规范、安全性、可维护性和潜在缺陷。
- **静态分析**：利用工具检查代码规则、复杂度、重复、依赖、漏洞和潜在错误，无需运行程序。
- **评审角色**：常见包括作者、主持人、评审人、记录员和负责人，具体设置取决于评审正式程度。

### 需求分析与需求评审

- **需求正确性**：需求应符合真实业务目标，不与政策或业务规则冲突。
- **需求完整性**：正常、异常、边界、权限、状态和非功能要求应尽量齐全。
- **需求一致性**：不同文档、原型、接口和业务规则之间不能相互矛盾。
- **需求明确性**：避免“尽快”“友好”“大量”等不可量化或有歧义的表达。
- **需求可行性**：在技术、成本、时间和合规约束下能够实现。
- **需求可测试性**：存在可观察、可衡量的验收标准，可以客观判断通过或失败。
- **需求可追踪性**：需求应具有唯一标识，并能追踪到设计、代码、用例和缺陷。
- **验收标准**：定义需求完成后必须满足的具体条件，是测试设计和验收的重要依据。
- **需求变更分析**：变更后应评估影响模块、接口、数据、用例、自动化脚本和回归范围。

## 测试计划 { #test-planning-and-resources }

测试计划把目标、范围、策略、人员、环境、进度和风险连接成可执行安排。计划应能随风险和交付节奏调整，而不是只在项目开始时编写一次。

- **测试目标**：说明本轮测试希望验证的内容和需要降低的主要风险。
- **测试范围**：明确测试项、不测试项、功能边界、平台和版本范围。
- **测试策略**：说明测试级别、类型、技术、回归方案和自动化方案。
- **资源与职责**：确定人员分工、环境、工具、设备和预算。
- **进度与里程碑**：安排测试设计、环境准备、执行、回归和报告时间。
- **准入与准出标准**：规定何时可以开始测试以及何时可以结束测试。
- **风险与应对**：识别影响质量和进度的风险，并制定缓解或应急方案。
- **交付物**：明确测试计划、用例、脚本、缺陷、报告等需要产出的材料。
- **沟通机制**：约定进度同步、缺陷评审、风险升级和发布决策方式。

## 测试场景与测试用例 { #scenarios-and-test-cases }

测试场景回答“要验证什么业务情境”，测试用例进一步规定条件、数据、步骤与期望。两者共同把分析结果变成可执行和可追踪的测试资产。

### 测试场景与测试点

- **测试条件（Test Condition）**：可通过一个或多个测试用例验证的功能、规则、质量属性或风险点。
- **测试场景（Test Scenario）**：从用户或业务视角描述需要验证的完整情境，粒度通常高于测试用例。
- **测试点**：对功能中需要检查的具体内容进行拆分，如输入校验、权限、状态变化和异常提示。
- **测试场景与测试用例的区别**：场景说明“需要验证什么业务情境”，用例进一步说明“在什么条件下、使用什么数据、怎样执行以及期望什么结果”。
- **快乐路径（Happy Path）**：用户输入和依赖都正常时完成目标的主流程。
- **异常路径（Unhappy Path）**：错误输入、依赖失败、权限不足或操作中断等非正常流程。
- **用户故事**：用简短形式描述角色、目标和价值，常配合验收标准指导测试。
- **业务流程**：验证主流程、分支流程、逆向流程、中断恢复和跨系统流转。
- **端到端场景**：从用户入口到最终业务结果完整验证系统及其依赖。
- **测试章程（Test Charter）**：为探索性测试定义目标、范围、关注风险和可使用资源。

### 测试用例

- **测试用例（Test Case）**：为验证特定目标而定义的一组前置条件、输入、步骤、预期结果和执行条件。
- **测试用例集（Test Suite）**：按模块、目标或执行批次组织的一组测试用例。
- **测试脚本**：可执行的详细手工步骤或自动化代码。
- **测试规程（Test Procedure）**：规定一组测试如何准备、按什么顺序执行以及如何收尾的操作说明。
- **测试夹具（Test Fixture）**：为测试准备的固定上下文，包括对象、数据、配置和依赖；通常由 Setup 创建、由 Teardown 清理。
- **Setup（前置准备）**：在单个测试或测试集执行前创建环境、对象和数据。
- **Teardown（后置清理）**：测试执行后释放资源、恢复状态并清理数据，防止相互污染。
- **测试运行（Test Run）**：在特定版本、环境和配置下执行一次测试用例或测试集的实例。
- **测试会话（Test Session）**：在限定时间内围绕明确目标开展的一段测试活动，常用于探索性测试。
- **测试包 / 测试集（Test Pack / Test Set）**：为某轮回归、版本或目标挑选并组织的用例集合，团队命名可能不同。
- **前置条件**：执行用例前必须满足的环境、账号、数据和系统状态。
- **预期结果**：根据测试依据提前定义的正确行为，应明确且可验证。
- **后置条件**：用例执行后系统应处于的状态，或需要进行的数据清理操作。
- **前置条件与测试夹具的区别**：前置条件描述测试开始前必须成立的状态；测试夹具是帮助建立和维护这些状态的具体数据、对象或机制。
- **原子性**：一个用例尽量聚焦一个清晰的测试目的，失败时易于定位原因。
- **可重复性**：在相同条件下重复执行，应得到一致结果。
- **独立性**：尽量降低用例之间的依赖，避免前一用例失败导致大量阻塞。
- **可维护性**：步骤清晰、复用适度，需求变化时容易定位和修改。

**常见测试用例字段**

- 用例编号
- 用例标题
- 所属项目 / 模块
- 关联需求编号
- 测试目标
- 前置条件
- 优先级
- 测试环境
- 测试步骤
- 测试数据
- 预期结果
- 实际结果
- 测试结果
- 后置条件
- 备注

**常见用例优先级**

- **P0 / 最高**：核心业务流程、系统可用性和重大风险场景。
- **P1 / 高**：重要功能、常用流程和关键异常场景。
- **P2 / 中**：一般功能和影响有限的场景。
- **P3 / 低**：低频、低风险或体验优化类场景。

## 测试设计技术 { #test-design-techniques }

测试设计技术帮助在无法穷尽所有组合时系统选择代表性测试。应根据规格、代码结构、历史缺陷和风险组合使用黑盒、白盒与经验方法。

### 黑盒测试用例设计方法

- **等价类划分**：将输入或输出划分为行为相同的有效、无效类别，从每类选择代表值测试。
- **边界值分析**：重点验证边界点、边界内外相邻值以及最小值、最大值，因为缺陷常发生在边界附近。
- **判定表法**：用条件与动作的组合表描述复杂业务规则，适合多条件组合场景。
- **因果图法**：分析输入条件与输出结果之间的逻辑关系，再转换为判定表和测试用例。
- **状态迁移法**：根据状态、事件、迁移和动作设计用例，适合订单、审批、账号锁定等状态型业务。
- **场景法**：围绕基本流、备选流和异常流设计端到端业务用例。
- **用例场景法**：根据参与者与系统的交互过程验证业务目标，常基于用例图或用户故事。
- **正交试验法**：使用正交表从大量因素与水平组合中选取有代表性的组合，减少组合数量。
- **组合测试 / 成对测试（Pairwise）**：优先保证任意两个参数取值组合至少被覆盖一次。
- **分类树法**：将输入域按分类和取值逐层拆分，再系统组合测试数据。
- **语法测试**：根据输入格式或语法规则生成合法、非法数据，适合解析器、协议和文件格式。
- **决策树法**：用树形结构描述条件选择和结果，适合分支复杂的业务规则。

### 白盒测试用例设计方法

- **语句覆盖**：确保每条可执行语句至少执行一次，是较弱的结构覆盖标准。
- **判定 / 分支覆盖**：确保每个判定的真、假结果都至少执行一次。
- **条件覆盖**：确保判定中每个基本条件的真、假取值都至少出现一次。
- **判定条件覆盖**：同时满足判定覆盖和条件覆盖。
- **条件组合覆盖**：覆盖判定中各基本条件的所有可能组合，组合数量可能快速增加。
- **修正条件 / 判定覆盖（MC/DC）**：证明每个基本条件都能独立影响判定结果，常用于高安全性系统。
- **路径覆盖**：覆盖程序中可能的执行路径；存在循环或复杂分支时通常无法穷尽。
- **循环覆盖**：验证不执行、执行一次、多次以及达到循环边界等情况。
- **基本路径测试**：依据控制流图和圈复杂度选取一组线性独立路径进行测试。
- **控制流图（CFG）**：用节点和边表示程序语句块及控制转移关系，是基本路径测试的基础。
- **圈复杂度（Cyclomatic Complexity）**：衡量控制流独立路径数量的指标，可用于估算基本路径数和代码测试难度。
- **数据流测试**：关注变量的定义、使用和销毁路径，发现未初始化、错误覆盖等问题。
- **变异测试（Mutation Testing）**：对代码植入微小变更，检查现有测试能否发现这些变化，以评价测试有效性。

> 覆盖率高只表示相关结构被执行过，不等于断言充分，也不代表业务逻辑一定正确。

### 基于经验的测试技术

- **错误推测法**：根据经验和历史缺陷推测容易出错的位置，如空值、重复提交、超长输入和网络中断。
- **检查表测试**：使用从规范、经验和历史问题沉淀出的清单开展系统检查。
- **探索性测试**：边学习、边设计、边执行，以测试人员的观察和判断快速发现未知问题。
- **缺陷攻击（Fault Attack）**：针对常见故障模式主动设计输入和操作以触发问题。
- **众测（Crowd Testing）**：借助大量不同地域、设备和背景的测试者发现多样化问题。

## 测试数据与环境 { #test-data-and-environment }

测试结果只有在数据和环境可控时才可解释、可复现。准备工作既要覆盖多样数据，也要记录版本、配置、依赖和清理方式。

### 测试数据

- **正常数据**：符合业务规则并代表常规用户行为的数据。
- **异常数据**：格式错误、逻辑冲突或不满足业务规则的数据。
- **边界数据**：最小值、最大值、临界点及其相邻值。
- **空值数据**：空字符串、Null、缺失字段、空集合等。
- **非法数据**：类型、长度、格式或字符集不符合要求的数据。
- **重复数据**：重复注册、重复提交、重复键值等场景的数据。
- **大规模数据**：用于验证分页、查询、导入导出和性能表现的数据。
- **特殊字符**：空格、换行、引号、Emoji、多语言字符、转义字符等。
- **关联数据**：满足或破坏主外键、上下游、状态依赖和业务约束的数据。
- **生产数据脱敏**：复制生产数据用于测试前，应移除或替换个人信息和敏感数据。
- **合成数据**：人工或工具生成且不对应真实用户的数据，更利于隐私保护和重复构造。
- **数据隔离与清理**：用例执行前后应保证数据可控，避免不同测试互相污染。

### 测试环境

- **环境组成**：操作系统、客户端、浏览器、服务器、中间件、数据库、网络、配置、第三方服务、账号和数据。
- **测试床（Test Bed）**：为执行测试组合起来的硬件、软件、网络、工具、测试数据和辅助程序的整体环境。
- **基线（Baseline）**：经过评审和确认、作为后续开发测试与变更比较依据的版本或配置集合；变更通常需要受控管理。
- **构建（Build）**：由特定源代码、依赖和配置生成的可部署或可测试软件制品。
- **发布版本（Release）**：经过评估并计划交付给用户或部署到目标环境的一组已标识制品。
- **开发环境**：开发人员编码和自测使用的环境，变化频繁。
- **测试环境**：供测试活动使用，应尽量稳定、可控且便于构造数据。
- **预发布环境**：尽量接近生产配置，用于上线前验证，但不能替代全部生产风险评估。
- **生产环境**：真实用户使用的环境，对验证操作、数据和权限必须严格控制。
- **环境一致性**：环境差异可能导致测试结果失真，需要记录版本、配置和依赖。
- **环境隔离**：不同测试任务或团队应避免数据、服务和配置互相干扰。
- **环境基线**：对可用的软硬件版本和配置建立明确基准，便于复现问题。
- **服务虚拟化**：用模拟服务替代难以获得、不稳定或成本高的真实依赖。
