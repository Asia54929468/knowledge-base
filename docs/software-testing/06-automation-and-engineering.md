## 自动化测试策略 { #test-automation-strategy }

自动化的价值来自快速、稳定、可重复的反馈，而不是替代所有人工测试。应优先选择稳定、高频和结果明确的场景，并持续治理失败定位与维护成本。

### 自动化测试

- **自动化测试**：使用脚本或工具自动执行测试步骤、校验结果并输出报告。
- **适合自动化的场景**：稳定且重复执行、回归频繁、数据组合多、结果明确、手工成本高的测试。
- **不适合优先自动化的场景**：需求频繁变化、只执行一次、主观体验强或自动化维护成本过高的场景。
- **单元自动化**：速度快、定位准确，适合验证代码级逻辑。
- **接口自动化**：稳定性通常高于 UI 自动化，适合业务规则和服务回归。
- **UI 自动化**：验证关键用户路径和跨层集成，但通常执行慢且维护成本较高。
- **端到端自动化**：覆盖完整业务链路，应选择少量高价值核心场景。
- **数据驱动**：将测试逻辑与输入和期望数据分离，用多组数据复用相同步骤。
- **关键字驱动**：用业务关键字组合测试流程，提高非编码人员可读性，但框架设计成本较高。
- **断言**：自动判断实际结果是否符合预期，是自动化测试有效性的核心。
- **等待机制**：优先使用条件等待，减少固定等待造成的慢速和不稳定。
- **测试隔离**：每个测试应尽量独立，并能自行准备和清理数据。
- **AAA 模式**：Arrange（准备数据和依赖）、Act（执行被测行为）、Assert（验证结果），是常见的自动化用例组织方式。
- **Given-When-Then**：Given 描述前置上下文，When 描述行为，Then 描述预期结果，常用于 BDD 和验收测试。
- **BDD（行为驱动开发）**：用业务可读的行为示例连接需求、开发和测试，强调协作，不只是编写 Gherkin 文本。
- **TDD（测试驱动开发）**：遵循“先写失败测试—编写最少实现—重构”的短循环驱动设计和开发。
- **参数化测试**：使用多组参数运行同一测试逻辑，减少重复代码并扩大数据覆盖。
- **属性测试（Property-based Testing）**：定义对大量输入都应成立的性质，由工具自动生成输入寻找反例。
- **模糊测试（Fuzz Testing）**：向程序输入大量随机、变异或生成的数据，寻找崩溃、异常和安全问题。
- **快照测试（Snapshot Testing）**：将当前输出与已保存快照比较，适合结构化输出或界面，但必须认真评审快照变化。
- **黄金主版本测试（Golden Master Testing）**：记录旧系统当前行为作为基准，与重构或迁移后的输出比较；它保留的是既有行为，不保证该行为本身正确。
- **Page Object 模式**：将页面元素定位和页面操作封装为对象，降低 UI 自动化用例与界面细节的耦合。
- **不稳定测试（Flaky Test）**：相同代码下结果时过时不过，需要定位时序、环境、数据或依赖问题，不能只靠重复运行掩盖。
- **自动化收益**：应综合执行频率、节省时间、维护成本、发现问题能力和反馈速度评价。
- **常见工具**：pytest、unittest、JUnit、TestNG、Playwright、Selenium、Appium、Postman / Newman 等。

## 测试隔离与测试替身 { #test-isolation-and-doubles }

测试隔离通过可替换依赖让用例在受控条件下运行。Dummy、Stub、Spy、Mock、Fake、测试桩和驱动程序各有用途，但替身不能代替必要的契约、集成和端到端测试。

### 测试替身、测试桩与测试辅助组件

- **测试替身（Test Double）**：测试中用于替代真实依赖对象或服务的统称，Dummy、Stub、Spy、Mock 和 Fake 都属于测试替身。
- **测试桩（Stub）**：替代被测模块所调用的下层模块，按预设规则返回固定或可控结果，使上层模块能在真实依赖未完成、不可用或难控制时被测试。
- **驱动程序（Test Driver）**：替代调用被测模块的上层模块，负责准备输入、调用被测模块并收集输出；常用于底层模块测试和自底向上集成。
- **测试桩与驱动程序的区别**：桩是“被被测对象调用”的假下游，驱动是“调用被测对象”的假上游。
- **Dummy（哑对象）**：只为满足参数、接口或结构要求而传入，测试中通常不会真正使用。
- **Spy（间谍对象）**：记录调用次数、顺序和参数，便于事后验证交互。
- **Mock（模拟对象）**：预先定义期望的交互，并在执行后验证调用是否符合约定，重点通常是行为验证。
- **Fake（伪对象）**：具有可工作的简化实现，如内存数据库或本地文件存储，功能可用但不适合生产。
- **Stub 与 Mock 的区别**：Stub 主要控制依赖返回什么，即状态验证；Mock 更关注是否按预期方式调用依赖，即交互验证。部分工具会混用名称，应看实际行为。
- **模拟器（Simulator）**：用软件近似模拟真实设备或系统的外部行为，不一定完整复制其底层实现和性能特性。
- **仿真器（Emulator）**：更强调复制目标硬件或运行环境，使原目标程序能够在其上运行，通常比模拟器更接近底层行为。
- **服务虚拟化（Service Virtualization）**：模拟完整外部服务及多种响应、延迟和故障，常用于接口与集成测试。
- **测试框架 / 测试支架（Test Harness）**：为执行测试提供驱动、测试桩、数据、日志、结果比较和报告等能力的整体工具集合。
- **测试脚手架（Scaffolding）**：为支持测试临时加入的辅助代码和基础结构，测试桩、驱动与数据构造器都可能属于其中一部分。
- **测试接缝（Test Seam）**：可以在不修改核心业务行为的情况下替换依赖或改变程序行为的位置，如依赖注入接口。
- **沙箱（Sandbox）**：与真实生产资源隔离、允许安全试验的受控环境，常用于支付、第三方 API 和安全测试。
- **使用目的**：隔离不稳定、昂贵、尚未完成或难以控制的依赖，提高测试速度、确定性和异常场景覆盖。
- **使用风险**：替身行为与真实系统不一致时可能产生错误信心，因此仍需适量契约、集成和端到端测试。

## CI/CD 与持续测试 { #continuous-testing-and-quality-gates }

持续测试把不同层级的检查嵌入交付流水线，以尽早反馈质量风险。执行顺序、质量门禁、制品晋级和失败信息决定流水线是否真正可用。

### CI/CD 与持续测试

- **持续集成（CI）**：频繁合并代码，并自动执行构建、静态检查和测试，尽早发现集成问题。
- **持续交付**：软件始终保持可发布状态，生产发布通常仍需人工批准。
- **持续部署**：通过流水线自动将满足条件的变更发布到生产环境。
- **持续测试**：在软件交付全过程中持续运行合适的测试并快速反馈质量风险。
- **质量门禁**：根据构建、测试、覆盖率、安全扫描和缺陷标准决定是否允许进入下一阶段。
- **分层流水线**：先执行快速检查和单元测试，再运行接口、集成、UI 和非功能测试。
- **失败反馈**：测试失败应快速通知相关人员，并提供日志、报告和可复现信息。
- **制品管理**：同一经过测试的构建产物应逐环境晋级，减少重新构建造成的差异。
- **蓝绿发布**：维护两套环境，通过切换流量降低上线和回滚风险。
- **金丝雀发布**：先向少量用户或流量发布，观察指标后逐步扩大范围。
- **功能开关**：将代码部署与功能开放分离，便于灰度、回退和实验。

## 环境工程化与可观测性 { #environment-engineering-observability }

版本控制、容器化、基础设施即代码和配置管理让环境可重建、可追踪。日志、指标与链路追踪则让失败能够被发现、关联和定位。

### 测试环境工程化

- **版本控制**：使用 Git 等工具管理代码、测试脚本、配置和文档变更。
- **容器化**：使用容器封装应用和依赖，提高环境一致性和创建速度。
- **基础设施即代码**：用代码管理环境资源和配置，使其可追踪、可重复创建。
- **配置管理**：分离代码与环境配置，妥善管理密钥和敏感信息。
- **日志**：应包含时间、请求标识、关键上下文和错误堆栈，便于跨服务追踪。
- **监控**：采集业务、应用和基础设施指标，及时发现异常趋势。
- **链路追踪**：通过 Trace ID 等标识关联跨服务调用，定位分布式系统问题。
- **可观测性**：结合日志、指标和追踪理解系统内部状态，并支持测试与生产诊断。
- **环境清理**：定期清理测试数据、临时资源和失效账号，避免污染及成本浪费。
