# 设计原则与技术选型

## 设计目标与原则

接口自动化框架不是简单地“用 requests 发请求，再用 assert 判断”。它需要稳定解决以下问题：

1. **请求复用**：统一处理域名、Header、Token、超时、SSL、路径参数与连接复用。
2. **分层解耦**：测试描述业务场景，API 层描述接口，HTTP 层处理传输。
3. **环境隔离**：切换环境只改配置，不改测试代码。
4. **数据驱动**：同一逻辑复用多组正常、异常和边界数据。
5. **状态管理**：合理复用登录态，并能刷新、清理失效缓存。
6. **失败可诊断**：正常日志简洁，失败时能看到脱敏后的请求响应上下文。
7. **可重复执行**：测试不依赖顺序，有副作用的操作能够回滚或清理。
8. **安全可控**：凭据不入库、敏感信息不落日志、生产环境禁止破坏性测试。

### 分层边界

| 层级 | 应该负责 | 不应该负责 |
| --- | --- | --- |
| 配置层 | 环境地址、超时、SSL、非敏感默认值 | 保存明文密码、编写业务断言 |
| HTTP 层 | URL、Session、Header、Token、传输异常 | 判断具体业务码 |
| API 层 | 接口路径、请求方法、参数映射 | 编写 pytest 用例、保存跨用例状态 |
| 数据层 | 输入、预期结果、场景标题 | 执行请求和复杂流程控制 |
| Fixture/Manager | 依赖注入、认证缓存、资源准备与释放 | 制造用例顺序依赖 |
| Testcase | 编排场景、调用 API、断言、清理 | 重复拼 URL 和公共请求逻辑 |
| 日志/报告 | 脱敏记录、失败诊断、结果展示 | 覆盖原始测试异常 |

## 技术选型

### 核心依赖

| 依赖 | 用途 |
| --- | --- |
| `pytest` | 测试发现、fixture、参数化、marker、hook |
| `requests` | HTTP Session 与请求发送 |
| `PyYAML` | 环境配置和测试数据读取 |

### 可选能力

| 依赖 | 用途 | 何时使用 |
| --- | --- | --- |
| `pytest-html` | 自包含 HTML 报告 | 小型项目、快速交付结果 |
| `allure-pytest` | 步骤、附件、趋势报告 | 团队项目和 CI 平台 |
| `jsonschema` | JSON Schema 校验 | 接口结构契约稳定时 |
| `pytest-xdist` | 并行执行 | 账号和测试数据已经隔离时 |
| `requests-mock` | Mock HTTP | 测试框架自身组件时 |
| `PyNaCl` / `cryptography` | 特定加密协议 | 登录或敏感数据需要客户端加密时 |

先完成“配置 → HTTP → API → 用例 → 报告”的最小闭环，再按实际问题引入扩展依赖。
